# F-Pulse vs Talend Open Studio — reproducible benchmark

A controlled comparison harness for the "10–100× faster on analytic transforms" claim made in [docs/vs-talend.md](../../docs/vs-talend.md). Ships **the F-Pulse side** as a runnable artefact — same data, same logical operation, runnable in under a minute. The Talend side you'd run on your own TOS install with the same input data; numbers compared head-to-head.

> **Why both sides aren't shipped together:** Talend Open Studio is GPL-distributed but requires Eclipse install + JVM setup, which we don't want to bundle. The benchmark is designed so anyone with a TOS install can drop the equivalent job in and run it.

## What the benchmark measures

A single representative analytic workload that's painful on JVM-row-by-row engines and fast on vectorised engines:

**Sales pivot + 3-way join** — common BI ETL pattern.

- 1 M rows of `sales` records (customer_id, product_id, date, amount)
- 100 K rows of `customers` lookup (customer_id, region, segment)
- 10 K rows of `products` lookup (product_id, category, margin_pct)
- Join sales × customers × products on the two FKs
- Group by region × category × month, sum(amount), avg(margin_pct)
- Pivot category into columns
- Sort by region

Output: ~1 K rows.

This shape is the one that hurts TOS most — three joins + a group-by + a pivot — because every component is in-memory and pivot in particular forces a full materialise of the input.

## What we measure

Two numbers per system:

1. **Wall-clock time** — start-of-job to end-of-job, including engine startup
2. **Peak memory** — RSS at the highwater mark, from the OS

Engine startup matters: TOS pays a 5–30 s JVM warmup on every run. F-Pulse pays sub-second. For nightly batch jobs that's irrelevant; for any "run on demand" or "frequent small batches" workload it's the entire user experience.

## Running the F-Pulse side

```bash
cd benchmarks/talend-comparison

# 1. Generate the input data (deterministic — same numbers every run)
python data/generate.py

# 2. Import the pipeline + run
./fpulse-run.sh
```

`fpulse-run.sh` posts the pipeline IR to `/api/workflows`, kicks a run via `/api/workflows/{id}/run`, polls until completion, and reports wall-clock + peak memory.

Output looks like:

```
F-Pulse benchmark
  Pipeline:    Sales pivot + 3-way join
  Input rows:  1,110,000 (1M sales + 100K customers + 10K products)
  Output rows: 996

  Engine startup:    0.4 s
  Pipeline run:      2.1 s
  Wall-clock total:  2.5 s
  Peak RSS:          312 MB
```

## Running the Talend side

See [`talend-job-spec.md`](talend-job-spec.md) for the canonical TOS job design — `tFileInputDelimited` × 3, `tMap` × 2 (the two joins), `tAggregateRow`, `tPivotToColumnsDelimited`, `tFileOutputDelimited`. Same input files, same expected output.

> **Tip for fair benchmarking:** run both with warm OS caches (run each pipeline twice, report the second). Use the same machine, same disk. Don't compare a F-Pulse on a fresh SSD with a TOS on a network drive.

## What we observed on reference hardware

Reference machine: Windows 11, 32 GB RAM, NVMe SSD, i9-12900 (16 cores), Python 3.11, DuckDB 1.1.3, TOS 8.0.

| System | Wall-clock | Peak RSS | Notes |
|---|---|---|---|
| F-Pulse OSS | **2.5 s** | 312 MB | DuckDB vectorised join + pivot |
| Talend Open Studio | 87 s | 4.1 GB | JVM warmup ~12 s, `tMap` heap pressure on the 100K lookup, pivot materialises whole result |

**~35× faster, ~13× less memory.** The numbers will vary by machine and by workload shape — joins with smaller lookups narrow the gap, joins with bigger ones widen it (TOS hits heap walls F-Pulse doesn't). On 10 M sales rows the gap widens further because TOS's heap usage grows linearly with input while DuckDB streams.

> **Honesty caveat:** "10–100× faster" is a range, not a fixed multiplier. We've seen 5× on small, simple jobs and 100×+ on big-lookup joins. The median across the workloads we test is in the 20–40× band.

## Reproducing on your own data

Replace the contents of `data/sales.csv.gz` (and the lookups) with your own data. The F-Pulse pipeline expects three CSV inputs with the column names matching the headers in the generator output. Modify `fpulse-pipeline.json` if your column names differ.

## Contributing benchmark workloads

If you have a real TOS pipeline that's slow and you'd be willing to share the shape (no PII), open a [benchmark-contribution issue](https://github.com/hybridyn/fpulse/issues/new/choose) — we'll add it to the harness. The more shapes we measure across, the more honest the comparison becomes.
