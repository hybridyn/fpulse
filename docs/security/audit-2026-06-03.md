## H1 — Password hashing uses single-round salted SHA-256

**Location:** `backend/fpulse/auth/models.py:36-46`

```python
@staticmethod
def hash_password(password: str) -> str:
    salt = secrets.token_hex(16)
    hashed = hashlib.sha256(f"{salt}:{password}".encode()).hexdigest()
    return f"{salt}:{hashed}"

def verify_password(self, password: str) -> bool:
    if not self.password_hash:
        return False
    salt, stored_hash = self.password_hash.split(":", 1)
    check = hashlib.sha256(f"{salt}:{password}".encode()).hexdigest()
    return check == stored_hash
```

**Why it's a problem:**

Salted SHA-256 prevents pre-computed rainbow tables, but each guess is a
single SHA-256 op — ~10 billion guesses/sec on a single modern GPU.
A typical 8-char password is crackable in minutes to hours; a 6-char
password in seconds. The salt forces the attacker to crack each hash
separately, but doesn't slow them down per-guess.

A leak of the auth store (file copy, backup theft, disk image) → every
password recoverable in attacker-bounded time.

**What modern standard practice is:**

- **bcrypt** with cost factor 12+ → ~250 ms per hash → 4 guesses/sec on
  the same GPU. A 6-char password takes years.
- **argon2id** — memory-hard, even more GPU-resistant. Preferred for
  greenfield.
- **PBKDF2-HMAC-SHA256** with 600,000+ iterations → ~200 ms per hash.
  Acceptable; the spec name often used as a stand-in for "modern
  password hashing" but slower than argon2id for the same brute-force
  cost.

**Compounding issue — the marketing claim is wrong:**

`frontend/src/components/pages/SettingsPage.tsx:1794` shows:
```
{ label: 'Credentials encrypted at rest (PBKDF2)', ok: true, plus: false }
```

This is doubly inaccurate:
1. The **encryption** (Fernet) uses AES-128-CBC + HMAC-SHA256, not PBKDF2.
   PBKDF2 is a key-derivation function — not an encryption algorithm.
2. **Password hashing** uses single-round SHA-256, not PBKDF2.

The Trust page (`docs/threat-model.md` §3.5) honestly describes the
current state; the UI claim does not. Either fix the implementation or
fix the claim (the audit recommends fixing both, in that order).

**Recommended fix:**

```python
# auth/models.py
import bcrypt

@staticmethod
def hash_password(password: str) -> str:
    return bcrypt.hashpw(password.encode('utf-8'), bcrypt.gensalt(rounds=12)).decode('ascii')

def verify_password(self, password: str) -> bool:
    if not self.password_hash:
        return False
    # Backward-compat: legacy 'salt:sha256' hashes upgraded on next login.
    if ':' in self.password_hash and not self.password_hash.startswith('$2'):
        return self._verify_legacy_sha256(password)
    try:
        return bcrypt.checkpw(password.encode('utf-8'), self.password_hash.encode('ascii'))
    except (ValueError, TypeError):
        return False
```

Plus a `_verify_legacy_sha256` helper that checks the old format and a
post-login hook that re-hashes with bcrypt on next successful login.
Add `bcrypt>=4.0` to `backend/requirements.txt`.

**Impact on existing installs:** zero password resets required.
Legacy hashes verified by the old method on first login → re-hashed
with bcrypt immediately after. Forced-rotation banner optional.

**Priority:** Before tagging v1.0.0.

## H2 — `api_source` and `http_request` have no SSRF protection

**Location:** `backend/fpulse/nodes/activities.py:215, 313` (and other
`urllib.request.urlopen` call sites in the same file)

```python
req = urllib.request.Request(url, method=method, headers=headers, data=data)
with urllib.request.urlopen(req, timeout=timeout) as resp:
    ...
```

`url` comes directly from `self.params["url"]` — user-controllable.

**Why it's a problem:**

A pipeline-authoring user can write an `api_source` pointing at
`http://169.254.169.254/latest/meta-data/iam/security-credentials/`
(AWS instance metadata), `http://localhost:6379/` (probe internal Redis),
or `file:///etc/passwd` (urllib doesn't refuse `file://` by default in
older Python versions).

In a single-user local install this is acceptable — the user already
has equivalent access. **The threat materialises when:**

- A multi-tenant F-Pulse+ deployment exists where pipeline authoring
  is more permissive than execution-level filesystem access.
- An RBAC setup where the `developer` role can author pipelines but
  shouldn't be able to read host metadata.
- A hosted version (planned) where pipeline contributions come from
  less-trusted users.

**The reference implementation already exists in the same repo:**

`backend/fpulse/connectors/ai_authoring.py:835` — `_ssrf_check_url()`
is a thorough, well-commented SSRF guard with:

- Scheme allowlist (`http`/`https` only)
- DNS resolution + RFC1918/loopback/link-local rejection
- Resolved-IP fetch to defeat DNS rebinding
- Redirect re-validation
- 2MB response size cap
- Opt-in escape via `FPULSE_OPENAPI_FETCH_ALLOW_PRIVATE=1`

This audit recommends extracting it to `fpulse/security/ssrf.py` (so it
can be imported without circular dependencies) and using it everywhere
the executor fetches a user-controlled URL.

**Recommended fix:**

1. Move `_ssrf_check_url` (+ `_resolve_safe_ip` if present + `SsrfBlockedError`)
   from `connectors/ai_authoring.py` to a new `security/ssrf.py` module.
2. Re-import it in `ai_authoring.py` so existing behaviour is unchanged.
3. Add the same check to every `urllib.request.urlopen` call site in
   `nodes/activities.py` (api_source, http_request, paginated fetch
   continuation).
4. Use a new env var `FPULSE_API_SOURCE_ALLOW_PRIVATE=1` (separate from
   the OpenAPI one — operators may want different policies).

**Priority:** Before tagging v1.0.0.

## M1 — File source accepts absolute paths

**Location:** `backend/fpulse/nodes/_path_utils.py:35-61`

```python
def resolve_input_path(file_path: str, data_dir: str) -> str:
    if not file_path:
        return file_path
    if os.path.isabs(file_path):
        return file_path  # ← absolute paths returned as-is
    primary = os.path.join(data_dir, file_path)
    ...
```

**Why it's an acceptable risk for v1.0 OSS:**

The single-user local install is the documented trust model. A user who
can author pipelines already has shell access to the host — they don't
need an arbitrary-file-read primitive in F-Pulse to read `~/.aws/credentials`.

**Why it becomes a real issue later:**

In F-Pulse+ multi-tenant scenarios, or any deployment where pipeline
authoring is gated to less-privileged users than the F-Pulse process,
a `file_source` pointed at `/etc/shadow` becomes a privilege-escalation
primitive.

**Recommended fix (for the multi-tenant scenario, not v1.0):**

Add `FPULSE_FILE_SOURCE_ALLOWED_ROOTS` env var listing comma-separated
prefixes. When set, every resolved path is checked against the list
and rejected if it escapes. Default unset = current behaviour (single-
tenant trust). Documented in `docs/threat-model.md` §4.2 today.

**Priority:** Document in v1.0; implement in v1.1 if F-Pulse+ multi-tenant
ships.

## L1 — UI text inaccurate about crypto algorithm

**Location:** `frontend/src/components/pages/SettingsPage.tsx:1794`
(plus likely siblings elsewhere — grep `PBKDF2`)

The UI claims "Credentials encrypted at rest (PBKDF2)" — the actual
implementation is Fernet (AES-128-CBC + HMAC-SHA256). PBKDF2 is a
key-derivation function used to turn passwords into keys; it is not an
encryption algorithm. Stating "PBKDF2" as the encryption mechanism is
either a misunderstanding or a copy-paste from a different stack.

The encryption itself is fine — Fernet is the recommended high-level
interface in the Python `cryptography` library, hard to misuse, AEAD.

**Recommended fix:** rename to "Credentials encrypted at rest (Fernet —
AES-128-CBC + HMAC-SHA256)" or "(authenticated encryption at rest)".

**Priority:** 5-minute fix any time. Independent of H1 — the encryption
is correct; just the label is wrong.

## Positive findings (audit credits)

1. **Encryptor design is good.** Versioned ciphertext prefix (`ENC:v1:`)
   enables key rotation without breaking old blobs. Sensitive-field
   allowlist means new credential fields default to encrypted unless
   explicitly named. Tolerates legacy plaintext on read so migration is
   transparent.

2. **Master key handling is good.** Mode-600 enforcement, parent dir
   chmod 700, refuse-to-start on group-readable file (POSIX). The
   one-time generation message includes a clear "back this up" warning.

3. **CI security tooling is comprehensive.** Bandit, pip-audit,
   npm audit, gitleaks, RBAC regression, security-headers pin. Missing
   only CodeQL — added in this Phase 1 (`.github/workflows/codeql.yml`).

4. **OpenAPI fetch SSRF defence is exemplary.** Detailed inline
   comments explain WHY each check exists. This is the model the
   audit recommends extending to `api_source` and `http_request`.

5. **Trust page surfaces claims with live endpoints.** Auditors can
   `curl /api/trust/posture` and verify the assertions themselves rather
   than trust a static report. This is a stronger signal than most
   pre-launch security marketing.

## Resolved this cycle

### H1 status — closed 2026-06-03

- `bcrypt>=4.0` added to `backend/requirements.txt`.
- `User.hash_password()` rewritten to `bcrypt.hashpw(..., gensalt(rounds=12))`.
- `User.verify_password()` accepts BOTH `$2b$...` (current) and `<hex>:<hex>` (legacy salted-SHA256) — no forced password reset.
- New `User.needs_rehash()` returns `True` for legacy hashes.
- `api/auth.py` login path checks `needs_rehash()` after successful verify and rehashes via `store.set_password(User.hash_password(...))`. Failure is logged, never blocks login.
- Both branches use `hmac.compare_digest` for timing-safety.
- Smoke-tested via `backend/tests/_phase1_smoke.py` (delete after the formal pytest test lands).

### H2 status — closed 2026-06-03

- New module `backend/fpulse/security/ssrf.py` with `check_url()`, `SsrfBlockedError`, and named env constants `OPENAPI_ALLOW_PRIVATE_ENV` + `API_SOURCE_ALLOW_PRIVATE_ENV` (separate escape hatches per feature).
- `connectors/ai_authoring.py` `_ssrf_check_url` is now a thin wrapper around the shared module — existing imports unchanged, behaviour preserved.
- `nodes/activities.py` calls `check_url()` before both `urllib.request.urlopen()` sites (`_do_request` for initial fetch, `_do_request_raw` for every pagination page so a compromised upstream can't redirect us into a private-network target on page 2+).
- Operators with internal API catalogs can opt in per-feature via `FPULSE_API_SOURCE_ALLOW_PRIVATE=1` (separate from the OpenAPI flag).
- Smoke-tested live: AWS IMDS, localhost, RFC1918, `file://`, credential-bearing URLs all return `SsrfBlockedError`.

### L1 status — closed 2026-06-03

- `frontend/src/components/pages/SettingsPage.tsx:1794` — label updated to `"Credentials encrypted at rest (Fernet — AES-128-CBC + HMAC-SHA256)"`.
- Source comment at line 1336 updated to match.
